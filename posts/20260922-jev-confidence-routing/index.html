Jev 사용법, 확신도로 자동·확인·사람 세 갈래 나누기

Jev 사용법 — 확신도로 세 갈래 나누기 (캐릭터는 GPT 이미지 생성)

Jev를 처음 부르면 답과 함께 숫자가 여럿 따라와요. 확률, 그리고 확신도(confidence). “이 숫자로 뭘 하라는 거지?” 하는 데서 막히기 쉬워요.

콜센터 접수 창구를 떠올려 보세요. 접수원은 문의를 읽고 도장 세 개를 찍어요. 어느 팀, 얼마나 화남, 급한가. 그리고 자신 없는 건 팀장에게 넘겨요. Jev는 이 접수원처럼 도장을 찍으면서, 얼마나 자신 있는지를 숫자로 같이 알려 줘요.
Jev 사용법의 핵심은 답을 받는 게 아니라, 확신도로 갈림길을 만드는 거예요.

편지를 자동·확인·사람 세 바구니로 나누는 접수 로봇 — 확신도 세 갈래 (GPT 이미지 생성)

🎯 이 글에서 얻는 것대상: Jev API를 처음 써 보려는 분
① 질문 셋을 한 번에 보내고 받는 법
② 확신도 읽기와 세 갈래 나누기
③ 한도·오류와 질문 쓰는 요령
준비물: 파이썬 3.10 이상 · TypeSafe API 키
2026년 10월 기준 · jev-1.13.0 · 공식 문서

1. SDK 설치하고 키 넣기

파이썬 SDK를 설치하고 API 키를 환경변수에 넣으면 준비가 끝나요. 1편에서 본 ‘고르기만 하는 AI’ Jev를 공식 문서의 예제 그대로 따라가요. 이 글의 값은 모두 문서의 예시 값이에요.

  1. 터미널에서 아래 한 줄로 SDK를 설치하세요.
pip install typesafe-sdk
  1. TypeSafe 대시보드에서 API 키를 받아 환경변수 TYPESAFE_API_KEY에 넣으세요.→ SDK가 이 값을 읽어요. 키를 코드에 직접 적지 않아도 돼요.

→ 이제 파이썬에서 TypeSafeClient() 하나로 Jev를 불러요. 모델은 따로 정하지 않으면 jev-latest예요.

2. 질문 셋을 한 번에 보내기

문의 한 통(상태, state)과 질문 셋(질문표, questions)을 한 번에 보내요. 공식 빠른 시작의 상태는 ‘3일째 Stripe 연동이 실패해 매출이 빠지고 있다, 빨리 도와 달라’는 고객 문의예요(원문은 영어). 여기에 질문 셋을 붙여요.
① department — 하나 고르기(Choice): 어느 팀이 맡나. 보기는 결제(billing)·기술(technical)·영업(sales)
② frustration — 단계 매기기(Score): 얼마나 화났나. 차분함 → 화났지만 정중함 → 매우 화남
③ is_urgent — 예/아니오(Noul): 급하다고 말하나

문서 표현으로 질문들은 ‘독립적으로, 병렬로 평가’돼요. 하나씩 세 번 보낼 이유가 없어요. 전체 파이썬 코드는 사이트판에 복사 버튼과 함께 있어요.

3. 돌아온 값 읽기

질문마다 답이 오고, Choice와 Score에는 확률과 확신도가 붙어요. 빠른 시작의 예시 값은 이래요.
① department → technical, 확신도 0.78, 확률은 기술 0.85 · 결제 0.15 · 영업 0
② frustration → 점수 1.0, 둘째 단계인 ‘화났지만 정중함’
③ is_urgent → 1.0, 급하다 쪽으로 100%

SDK 없이 HTTP로 직접 보내도 모양은 같아요. API 문서의 응답 예시를 줄이면 이래요.

{
  "model": "jev-1.13.0",
  "answers": {
    "is_urgent": {"noul": 0.95}
  },
  "usage": {"input_tokens": 296,
            "output_tokens": 20}
}

세 가지가 눈에 들어와요.
① 별명 jev-latest로 보내면 실제 버전 jev-1.13.0이 돌아와요.
② 응답에 글이 한 줄도 없어요. 숫자와 이름뿐이에요.
③ 출력 토큰이 찍히지만 모델 문서상 출력 요금은 없어요. 입력 100만 토큰당 0.042달러만 내요.

4. 확신도 읽는 법

확신도는 확률이 한쪽에 얼마나 몰렸는지를 0~1 숫자 하나로 접은 거예요. 다 몰리면 1, 고르게 퍼지면 0이에요. Choice의 계산식은 문서에 나와 있어요. 보기가 n개이고 가장 큰 확률이 p라면 (n × p − 1) ÷ (n − 1)이에요.

보기가 셋이면 이렇게 돼요.
① 기술 1.0 · 나머지 0 → 확신도 1.0
② 기술 0.85 · 결제 0.15 · 영업 0 → 0.78 (위 예시 응답 그대로)
③ 셋이 3분의 1씩 → 0

감정 구름의 높이를 세 구간 자로 재는 로봇 — 확신도를 숫자로 읽는 장면 (GPT 이미지 생성)

Score는 계산이 조금 달라요. 단계에 순서가 있어서, 이웃 단계로 갈리면 덜 깎이고 양 끝으로 갈리면 더 깎여요. 문서 예시에서 심각도 세 단계의 확률이 0 · 0.57 · 0.43으로 갈리면 점수는 1.43, 확신도는 0.35로 낮게 나와요. 점수와 확신도는 늘 같이 보세요. 점수가 애매하면 확신도가 낮아요.

Noul에는 확신도가 따로 없어요. 값 자체가 ‘예’일 확률이라, 0.5에 가까울수록 모르겠다는 뜻이에요.

5. 확신도로 세 갈래 나누기

확신도가 있으니 코드가 갈림길을 만들 수 있어요. 공식 문서 ‘확신도’ 페이지가 출발점으로 권하는 세 갈래예요.

확신도코드가 할 일
높음사람 없이 자동으로 실행 — 도장 찍고 바로 전달
중간조심해서 진행 — 확인 요청, 검토 표시, 정보 더 모으기
낮음실행하지 않음 — 사람에게, 다시 묻기, 다른 시스템으로

문턱을 어디에 둘지는 일의 무게가 정해요. 확신도 페이지의 예제 코드는 0.5를 바닥으로 두고, 그 아래는 사람에게 넘겨요. 그 위에서는 되돌리기 어려운 일일수록 문턱을 높여요.

‘확신도 기반 라우팅’ 패턴의 은행 예제는 이래요. 잔액 조회는 0.6만 넘으면 보여 줘요. 틀려도 잔액을 한 번 더 듣는 정도라서요. 송금 승인은 0.85를 넘어야 자동으로 하고, 그 아래면 ‘확인하시겠어요?’를 띄워요.

Jev 확신도 세 갈래 — 상태와 질문표를 보내면 답·확률·확신도가 오고, 코드가 자동·확인·사람으로 나눈다 (직접 제작)

0.5, 0.6, 0.85는 문서 예제의 숫자일 뿐, 내 일에 맞는 값은 따로 있어요.

💡 핵심문턱은 정답이 아니라 출발점이에요. 보수적으로 시작해 내 데이터로 시험하고 조정하세요.

6. 질문 잘 쓰는 요령

넓은 판단은 좁은 질문 여러 개로 쪼개세요. 문서의 원칙은 ‘넓은 판단을 좁고 타입이 정해진 질문들로 쪼개고, 지시와 기준을 명시하라’예요. 판단은 Jev가, 흐름은 코드가 맡아요.

첫째, 조건 하나에 질문 하나

❌ 이렇게 말고

고객이 화가 났고, 환불을 요구하나?

두 조건을 한 번에 판단하니 값의 뜻이 흐려져요. 둘로 나눠 묻고, 합치는 건 코드가 해요.

⭕ 이렇게

고객이 화가 났나?

환불 요구는 따로 물어요.

고객이 환불을 요구하나?

둘째, ‘예’가 ‘있다’ 쪽이 되게 ‘개인정보가 없는가?’처럼 거꾸로 물으면 뒤에서 읽는 코드가 반대로 해석하기 쉬워요. ‘개인정보가 있는가?’로 물으세요.

셋째, Score 단계는 정도가 아니라 상황으로 ‘약간·보통·매우’ 대신 ‘우회 방법이 있다 / 없다’처럼 Jev가 맞춰 볼 상황을 적으세요. 순서가 없는 것(팀 이름)은 Choice로, 예/아니오는 Noul로 물어요.

넷째, 상태에는 판단에 필요한 것만 문서는 관련 있는 맥락만 넣어야 모델이 방해받지 않는다고 해요. 계산·날짜·개수 같은 일은 Jev에게 맡기지 말고 코드가 해요.

문서는 이 원칙으로 네 가지 패턴을 권해요. 한 번에 여러 질문을 미리 묻기, 확신도로 가르기, 여러 Score를 코드가 합치기, 의도를 Choice로 분류해 처리기 고르기예요.

7. 한도와 요금 알고 시작하기

쓰기 전에 한도를 알아 두면 오류를 줄일 수 있어요. 모델 문서와 API 문서에 적힌 값이에요(2026년 10월 7일 확인).

항목값
상태 크기요청 전체 64k 토큰, 상태와 가장 긴 질문을 합쳐 32k 토큰
입력글자만 — 문자열, JSON 객체, 문자열 배열
Choice 보기최대 255개
Score 단계2~10개
속도 한도초당 10만 토큰, 초당 80요청 (수시로 조정 중)
요금입력 100만 토큰당 0.042달러, 출력 무료

속도 한도는 9월 22일 이 글을 처음 쓸 때(초당 25만 토큰, 분당 1,200요청)와 달라졌어요. 문서도 수요에 따라 예고 없이 바뀔 수 있다고 밝혀요.

막힐 때

401 오류가 나요
원인: API 키가 없거나 잘못됐어요.
해결: 환경변수 TYPESAFE_API_KEY에 키가 들어 있는지, 요청의 Authorization 머리값을 확인하세요.

422 오류가 나요
원인: 요청 형식이 틀렸어요. 필수 항목이 빠졌거나 질문 모양이 잘못된 경우예요.
해결: 오류 본문이 어느 항목이 문제인지 알려 줘요. 그 항목부터 고치세요.

429나 529 오류가 나요
원인: 429는 속도 한도 초과, 529는 서비스 과부하예요.
해결: 바로 다시 보내지 말고 지수 백오프(잠깐 쉬고, 다음엔 두 배 쉬고)로 재시도하세요. 공식 SDK는 기본 설정으로 이걸 알아서 해요.

한국어 문의에서 결과가 어긋나요
원인: Jev의 주 학습 언어는 영어예요. 문서는 한국어 같은 다른 언어도 받지만 정확도가 같지는 않다고 밝혀요.
해결: 내 데이터로 먼저 시험하고, 확신도로 가를 때 문턱을 더 보수적으로 두세요.

✅ 한눈에 정리① 상태와 질문표를 보내면 답이 한 번에 와요
② 확신도는 ‘모르겠다’를 숫자로 말한 것
③ 높으면 자동, 중간은 확인, 낮으면 사람
④ 문턱은 출발점 — 내 데이터로 조정해요

자주 묻는 질문

Q. 파이썬을 꼭 써야 하나요?

아니요. SDK 없이 HTTP로 직접 보낼 수 있어요. 공식 문서의 v1/systemone 주소로 3번에서 본 JSON 모양 그대로 주고받아요.

Q. Noul에는 왜 확신도가 없나요?

Noul 값 자체가 ‘예’일 확률이라서요. 0.5에 가까우면 모르겠다는 뜻이에요.

Q. 질문을 하나씩 나눠 보내는 게 더 정확하지 않나요?

같은 상태에 대한 질문은 한 요청에 모으는 게 문서의 권장이에요. 질문들은 독립적으로, 병렬로 평가돼서 한 질문의 답이 다른 질문에 끼어들지 않아요.

Q. 요금은 어떻게 매기나요?

입력 토큰에만 매겨요. 2026년 10월 7일 모델 문서 기준 100만 토큰당 0.042달러이고, 출력은 무료예요.

from typesafe_sdk import Choice, Noul, Score, TypeSafeClient

client = TypeSafeClient()   # 환경변수 TYPESAFE_API_KEY 를 읽고, 모델은 기본 jev-latest
ticket = "3일째 Stripe 연동이 계속 실패해요. 매출이 빠지고 있어요. 빨리 도와주세요."  # 상태(state)

response = client.system_one(
    state=ticket,
    questions={
        "department": Choice(                       # 하나 고르기
            instructions="어느 팀이 맡아야 하나",
            criteria={"billing": "결제·구독 문제", "technical": "버그·연동 문제", "sales": "가격·계정 문의"},
        ),
        "frustration": Score(                       # 단계 매기기 (낮은 단계 → 높은 단계 순서)
            instructions="고객이 얼마나 화나 보이나",
            criteria=["차분히 사실만 말함", "화났지만 정중함", "매우 화남, 거친 표현"],
        ),
        "is_urgent": Noul(                          # 예/아니오
            instructions="급하다거나 시간이 촉박하다고 말하고 있나",
        ),
    },
)

print(response.answers["department"].choice)   # "technical"  (문서 예시: 확신도 0.78, 확률 technical 0.85 · billing 0.15 · sales 0.0)
print(response.answers["frustration"].score)   # 1.0          (= "화났지만 정중함")
print(response.answers["is_urgent"].noul)      # 1.0
