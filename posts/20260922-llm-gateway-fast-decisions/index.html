LLM 게이트웨이 판정 API, Jev 계약을 옮겨 붙인 기록

LLM 게이트웨이 — 판정 창구를 하나 더 낸 기록 (캐릭터는 GPT 이미지 생성)

‘이 문의는 어느 팀?’, ‘이 리뷰 지적은 진짜인가?’ 같은 질문에는 긴 글이 필요 없어요. 그런데 이런 판정도 글을 만드는 창구에서 수 초에서 수십 초씩 기다려 받고 있었어요.

은행에 창구가 하나뿐이라고 해 보세요. 잔액 확인은 10초면 되는데, 앞사람 대출 상담이 30분이면 다 같이 기다려요. 그래서 은행은 빠른 창구를 따로 내요. 상담은 원래 창구로, 확인·판정은 빠른 창구로요.
그래서 제가 만들어 쓰는 LLM 게이트웨이에 판정 전용 창구를 하나 더 냈어요. 계약은 Jev의 것을 그대로 가져왔어요.

게이트웨이 v0.1.99(2026년 9월 22일) 기준

1. 문제: 판정도 글 창구에 줄을 섰다

게이트웨이에 창구가 하나뿐이라, 판정만 필요한 요청도 글을 만드는 줄에 섰어요. LLM 게이트웨이는 여러 앱(코드 리뷰 도구, 문서 도우미, 자동화 스크립트)이 AI를 부를 때 거치는 단 하나의 주소예요.

앱은 어느 모델을 쓸지 몰라도 돼요. 게이트웨이가 연결된 모델을 골라 주고, 키와 동시 접속 수와 대기열을 관리해요.

문제는 이 창구가 하나였다는 거예요. 글을 만드는 요청과 판정만 필요한 요청이 같은 줄(/v1/chat/completions)에 섰어요.

2. 한 일: 판정 창구를 하나 더 냈다

2026년 9월 22일, 판정 전용 창구 POST /v1/decisions를 새로 냈어요. 상태와 타입 질문(noul·choice·score)을 보내면, 글 대신 답과 확률이 돌아와요. 글 창구는 그대로 두었어요.

새 형식을 발명하지 않고, Jev의 계약을 그대로 채택한 게 핵심 결정이었어요. 2편에서 본 대로 그 계약은 이미 잘 설계돼 있어요(질문 셋, 확률, 확신도). 그리고 앱 입장에서는 게이트웨이 뒤가 Jev든 다른 모델이든 요청·응답 모양이 같아야 창구를 둔 의미가 있어요.

판정 창구가 지키는 한도는 공식 한도를 따르거나 조금 더 보수적이에요.

항목판정 창구의 한도
질문 수최대 32개
Choice 보기 · Score 단계보기 최대 255개 · 단계 2~10개
질문 문장4,000자
상태기본 20만 자에서 먼저 자름 (공식 한도는 요청 64k 토큰)
Jev를 글 창구로 부르면400 오류 — 모델이 없는 게 아니라 능력이 없는 것

LLM 게이트웨이에 낸 두 번째 창구 — 앱은 창구만 고르고, 뒤의 두 경로는 게이트웨이가 고른다 (직접 제작)

3. 두 경로: 진짜 Jev와 흉내

같은 계약을 두 경로가 내게 만들었어요. 진짜 Jev와, 챗 모델의 흉내(에뮬레이션)예요. Jev는 클라우드 서비스라서, 바깥 클라우드에 닿지 않는 회사망에서는 쓸 수 없어요. 어떤 곳에서는 되고 어떤 곳에서는 안 되는 창구는 창구가 아니죠.

경로하는 일
① 진짜 Jev (개인 PC 모드)요청을 Jev 공식 주소로 그대로 넘긴다 — 보정된 확률, calibrated: true
② 흉내 (회사망 모드)빠른 챗 모델에 ‘JSON으로만 답하라’고 시켜 같은 모양으로 정리 — 자기보고 확률, calibrated: false

흉내 경로는 지원하는 모델에 응답 형식(json_schema)까지 강제하고, 생각(추론) 기능은 끄고, 도구 없이 한 번에 불러요. 단, 확률은 그 모델이 스스로 적어 낸 숫자예요. 그래서 응답에 calibrated: false를 붙이고, ‘이 확률로 문턱 분기를 하지 말고 답 값만 믿으라’고 문서에 적었어요. JSON이 어긋나면 한 번만 다시 시도하고, 그래도 안 되면 조용히 추측하지 않고 502 오류로 돌려줘요.

다른 로봇의 가면을 든 배우 로봇 — 흉내 경로는 흉내라는 걸 응답에 표시한다 (GPT 이미지 생성)

앱이 model: “auto”로 보내면 게이트웨이가 후보를 차례로 봐요. 개인 PC에서는 Jev → 로컬 모델 → 클라우드 소형 모델 순이고, 회사망에서는 그 안의 소형 모델부터예요. 연결돼 있고, 허용되고, 지금 받을 수 있는 첫 모델이 답해요. 앱은 어느 쪽이 답했는지 응답의 calibrated 값으로 알 수 있어요.

4. 결과: 빨라진 건 모델이 아니라 흐름

릴리스 노트에 굵게 적어 둔 문장이 있어요. ‘텍스트 생성 자체는 바뀌지 않는다.’ 판정 창구를 냈다고 글 창구가 빨라지지는 않아요. 이득은 두 군데서 와요.

① 판정을 옮긴다. 글 창구에서 ‘이 리뷰 지적이 진짜인가?’를 문장으로 받아 파싱하던 것을, 판정 창구에서 noul 0.93 같은 숫자 하나로 받아요.
② 판정으로 생성을 건너뛴다. ‘이 청크는 검토할 가치가 있나?’의 답이 아니오면 뒤의 긴 생성을 아예 하지 않아요. 이쪽이 더 큰 이득이에요.

릴리스 노트에 적은 실측 기대치는 이래요. 환경에 따라 달라요. Jev 0.1~0.5초 · 로컬·소형 챗 모델 0.2~2초 · 상주 세션 없는 CLI 모델 3~8초

💡 핵심빨라지는 건 모델이 아니라 앱의 흐름이에요. 판정은 판정 창구로, 글이 필요한 것만 글 창구로 보내세요.

5. 키와 기록: 남기지 않는 것

Jev를 붙이면서 지킨 규칙은 게이트웨이의 다른 프로바이더와 같아요.
① API 키는 화면(설정 패널)에서 입력하고 암호화 저장소에만 둬요. 환경변수·코드·로그에는 두지 않아요.
② 로그에는 모델 이름·걸린 시간·질문 개수만 남겨요. 상태와 질문 문구는 남기지 않아요. 상태에는 고객 문의 원문이 들어가니까요.
③ 회사망 모드에서는 Jev 프로바이더가 목록에서 아예 사라져요. 연결 시도조차 하지 않게요.
④ 429(속도 초과)·529(과부하)는 2초 뒤부터 지수 백오프로 다시 시도해요. 2편에서 본 공식 지침 그대로예요.

6. 검증과 남은 숙제

개발 PC 실환경에서 두 경로를 모두 돌려 확인했어요. 자동 테스트에 더해 Jev 네이티브를 영어·한국어·객체 상태로, 흉내를 클라우드 소형 모델 둘로 돌렸어요. auto 후보 순서, 오류 코드, 그리고 로그에 키와 상태가 남지 않는지도 봤어요.

한국어 상태로도 답이 왔지만, Jev 문서는 영어 외 언어의 정확도가 같지 않다고 하니 판정 품질은 앱마다 따로 봐야 해요.

남은 숙제도 있어요.
① 앱 쪽 전환은 이제 시작이에요. 창구를 냈다고 앱이 저절로 옮겨 오지 않아요. 코드 리뷰 도구의 ‘지적이 진짜인가’ 검증과 청크 우선순위 매기기가 첫 후보예요.
② 판정 결과 캐시(같은 상태·질문이면 재사용)와 리뷰 전 선별(판정이 아니오면 건너뜀)은 후속 후보로 남겨 두었어요.
③ Jev는 새 제품이라 요금·한도·버전이 바뀔 수 있어요. 실제로 10월 7일 문서의 속도 한도는 9월과 달라져 있었어요. 게이트웨이는 응답에 실린 실제 버전(jev-1.13.0)을 기억해 앱이 고정할 수 있게 보여 줘요.

⚠️ 주의흉내 경로의 확률로 0.9 같은 문턱을 걸지 마세요. calibrated: false를 무시하면 1편에서 본 ‘자신만만한 환각’이 그대로 돌아와요.

적용해 보기

여러 앱이 쓰는 AI 창구가 있다면, 이 순서로 판정 창구를 따져 보세요.

  1. 앱들이 AI에게 보내는 요청을 ‘글이 필요한 것’과 ‘판정만 필요한 것’으로 나눠 보세요.→ 판정만 필요한 요청이 생각보다 많아요.
  2. 판정 요청을 상태 + 질문 셋(어느 것·몇 단계·예/아니오)으로 다시 적어 보세요.→ 이렇게 적히지 않는 것은 글이 필요한 요청이에요.
  3. 창구를 하나 더 내되, 계약은 발명하지 말고 이미 있는 것을 채택하세요. 클라우드에 닿지 않는 환경이면 흉내 경로를 함께 두고 calibrated: false를 꼭 붙이세요.→ Jev의 계약이 좋은 출발점이에요.
  4. 첫 앱 하나만 옮기고, 두 창구의 대기 시간을 비교하세요.→ 숫자로 확인한 뒤에 다음 앱을 옮겨요.

자주 묻는 질문

Q. 판정 창구를 내면 글 생성도 빨라지나요?

아니요. 릴리스 노트에 적은 대로 텍스트 생성 자체는 바뀌지 않아요. 판정을 옮기고, 판정으로 불필요한 생성을 건너뛰는 만큼 앱의 흐름이 빨라져요.

Q. 왜 새 형식을 만들지 않고 Jev의 계약을 썼나요?

이미 잘 설계된 계약이고, 뒤에서 어느 모델이 답하든 앱이 보는 모양이 같아야 창구를 둔 의미가 있어서요.

Q. 흉내 경로의 확률은 아예 못 쓰나요?

답 값(choice·score)은 쓰되, 확률로 문턱 분기는 하지 말라고 문서에 적었어요. 모델이 스스로 적어 낸 숫자라 보정되지 않았거든요.

Q. Jev 모델을 글 창구로 부르면 어떻게 되나요?

400 오류로 돌려보내요. 모델을 못 찾은 게 아니라, 글을 만드는 능력이 없는 모델이라서요.
