이 글에는 제휴 링크가 없고 OpenAI·앤트로픽과 아무 관계가 없습니다. 제가 직접 만든 중계기의 개발 기록을 바탕으로 썼습니다. 삽화는 GPT 이미지 생성, 도식은 직접 제작했습니다.

AI 페어 프로그래밍, 하루 만에 첫 버전을 만든 이삿날 기록 (LLM 중계기 개발기)

AI 페어 프로그래밍 — 하루 만에 만든 첫 버전 (캐릭터는 GPT 이미지 생성)

AI 코딩 도우미와 같이 만들면 하루 만에 쓸 만한 프로그램이 나올까요? “AI가 다 짜 주면 사람은 뭘 하지?”라는 궁금증도 따라와요. 지난 3편에서는 중계기가 여는 ‘OpenAI 호환’ 창구가 왜 표준 콘센트가 됐는지 이야기했어요. 오늘은 그 창구를 처음 연 하루의 기록이에요.

이삿날을 떠올려 볼게요. 아침에 상자를 열고, 꽂아 보니 안 맞는 플러그를 고치고, 하나를 고치면 다음 게 보여요. 그래도 누울 때쯤이면 그 집에서 하룻밤은 지낼 수 있게 되죠. 제 LLM 중계기의 첫날이 꼭 그랬어요.
아침 8시 8분에 첫 버전이 저장됐고, 밤 10시 23분 v0.1.16까지 저장 기록 54개가 쌓였어요. 그중 28개에 AI가 공동 작성자로 올라 있어요.

1. 하루를 한 장으로

첫날은 아침 첫 버전, 오전의 윈도 고장, 오후 판 9개, 저녁과 밤 판 7개로 흘러갔어요. 아래 그림에서 노란 점 하나가 새로 내놓은 판(버전) 하나예요.

AI 페어 프로그래밍 첫날 타임라인 — 아침 첫 버전부터 밤 v0.1.16까지 (직접 제작)

글에 자주 나오는 낱말 세 개를 먼저 짚을게요.

낱말뜻
커밋 (commit)무엇을 왜 바꿨는지 메모를 붙여 남기는 저장 기록 — 게임의 세이브 포인트
PR 합치기따로 작업한 변경을 본 줄기에 합치는 절차
판 (버전)쓰는 사람에게 내놓는 묶음의 번호 — v0.1.0 다음이 v0.1.1

그날의 저장 기록 54개는 직접 작업한 기록 29개와 PR 합치기 기록 25개로 이뤄져 있어요.

2. 아침: 첫 버전과 모델 13개

아침 8시 8분, 여러 AI를 ‘OpenAI 호환’ 창구 하나 뒤에 세운 첫 버전(v0.1.0)이 저장됐어요. 저장 메모를 쉬운 말로 옮기면 네 가지예요.

① AI마다 연결 방식이 달라서, 같은 약속으로 다루는 AI별 어댑터를 만들었어요. 5편에서 다룰 어댑터의 첫 모습이에요.
② ‘OpenAI 호환’ 창구를 열어 연결된 AI들의 모델 목록을 한데 모으고, 그 형식 그대로 대화를 주고받게 했어요.
③ 관리 화면은 LM Studio 화면의 잘된 점만 빌렸어요.
④ 로그인 정보는 내 컴퓨터 안에 암호화해 저장하고, 기록에는 비밀 값을 가려서 남겨요.

실제로 붙여 보니 LM Studio 6개, Codex 4개, Claude 3개, 모두 13개 모델이 창구 하나의 목록에 나란히 떴어요. 7분 뒤에는 연결 확인용 시험 호출이 “pong” 한 마디로만 짧게 답하게 손질했어요. 탁구공을 쳤을 때 받아치는지만 보는 셈이에요.

3. 오전: 윈도에서 처음 켜 보다

중계기는 맥에서 만들었지만 실제로 쓸 컴퓨터는 윈도였고, 켜 보자마자 고장이 줄줄이 나왔어요. ‘여기선 되는데 저기선 안 되는’ 고장이 오전에만 넷이었어요.

10시 21분 — 켜자마자 꺼짐 윈도의 D: 드라이브 글자를 http: 같은 주소의 앞머리로 착각했어요. 20편에서 자세히 다뤄요.
10시 40분 — 두 컴퓨터가 부품 목록을 서로 고쳐 씀 맥과 윈도의 개발 도구(npm) 버전이 달라, 한쪽이 넣은 한 줄을 다른 쪽이 지우기를 되풀이했어요.
12시 36분 — 깔려 있는데 ‘미설치’ 윈도에서는 Codex가 .cmd라는 껍데기 파일로 깔리는데, 중계기가 그걸 실행하지 못하고 “없다”고 판단했어요.
1시 44분 — 8초 멈춤과 401 명령창에선 바로 답하는 Codex 버전 확인이, 중계기 안에서는 8초로 정해 둔 기다림 시간을 넘겼어요. 윈도 명령 해석기(cmd)를 직접 불러 실행하게 바꿔 해결했어요. 로그인했는데도 Claude가 401(인증 실패)을 내던 문제도 같은 판에서 잡았어요. 환경 설정에 남은 API 키가 로그인보다 먼저 쓰였거든요(8편).

오전의 수정은 모두 v0.1.0 번호를 단 채 이어졌고, 처음 번호를 올린 판이 오후 1시 45분의 v0.1.1이에요.

4. 오후: 첫 답이 늦은 문제를 재다

오후에 가장 오래 붙잡은 건 첫 답이 너무 늦게 오는 문제였고, 답은 재 본 숫자에서 나왔어요. 1시 45분 v0.1.1부터 5시 v0.1.9까지, 세 시간 남짓 동안 아홉 판이 올라갔어요.

v0.1.2부터 v0.1.5까지는 걸리는 시간을 단계별로 재며 “띄우는 시간인가”, “AI가 생각을 너무 많이 하나” 같은 가설을 하나씩 지웠어요. 답은 3시 20분의 v0.1.6에서 나왔어요. 새 대화를 열 때마다 준비 시간이 크게 들었고, 열어 둔 대화를 다시 쓰자 두 번째 호출부터는 몇 초 만에 답이 왔어요. 그래서 연결하자마자 대화를 미리 데워 두는 워밍업(warm-up)을 넣었어요. 켜 둔 채 쓰는 방식은 6편에서 따로 풀어요.

대화를 다시 쓰면 앞 내용이 섞일 수 있어서, 요청마다 필요한 내용을 다 담아 보내고 ‘세션 리셋’ 버튼도 달았어요.

v0.1.7은 ‘HTTP 400’ 한 줄 대신 AI 쪽이 보낸 오류 원문을 그대로 전하게 했어요(18편).
v0.1.8은 연결 해제와 모델별 끄기를 넣었어요. 저장 메모에 제 말이 그대로 남아 있어요. “방금 Codex를 안 쓰게 하려고 했더니 방법이 없었어.”

5. 저녁과 밤: 짐 정리와 마지막 고장

저녁부터는 이사로 치면 ‘다른 사람이 와서 지내도 되게’ 정리하는 시간이었어요.

6시 38분 v0.1.10 — 다른 화면에 다녀와도 시험 결과가 남게 했어요.
7시 9분 v0.1.11 — 압축(zip)만 풀면 바로 실행되는 배포판이에요. 두 번 켜면 꺼지던 문제도 고쳐, 이제는 이미 켜진 쪽 화면을 열어 줘요.
8시 54분 v0.1.13 — “설정 파일을 직접 열어 고치세요”라는 안내가 남아 있으면 실패하는 검사를 붙였어요.
9시 14분 v0.1.14 — 연결된 모델과 주소가 채워진 예제 코드를 보여 주는 ‘개발자’ 탭을 만들었어요.
10시 4분 v0.1.15 — 꺼도 뒤에서 살아남은 프로세스(좀비)가 다음 실행을 막던 문제를 고쳤어요. 21편에서 다뤄요.
10시 22분 v0.1.16 — 압축판에서만 Claude가 안 붙었어요. 맥에서 만든 윈도용 압축 파일에 맥용 부품이 들어가 있었거든요. 이미 깔린 Claude 명령어 도구를 쓰게 바꿨더니 압축 파일도 180MB → 113MB로 줄었어요.

그다음 판 v0.1.17은 날짜를 넘긴 새벽 1시 9분에 올라갔어요. 이삿날 밤은 생각보다 길었던 셈이에요.

6. AI와 사람이 나눈 일

직접 작업한 기록 28개에는 하나도 빠짐없이 AI(Claude)가 공동 작성자로 올라 있어요.

  • 29개 중 저장소를 만들 때 생긴 두 줄짜리 첫 기록을 뺀 28개 모두에 ‘Co-Authored-By’(공동 작성자) 꼬리표가 붙어 있어요.
  • 아침 두 건은 Claude Fable 5, 나머지 26건은 Claude Opus 4.8이에요. Codex는 이날 공동 작성자가 아니라 중계기에 연결되는 쪽이었어요.

밤늦게 하이파이브하는 로봇과 작은 AI 도우미 — 사람과 AI가 짝으로 일한 첫날 (GPT 이미지 생성)

역할은 저장 메모에 그대로 드러나 있어요.

AI(Claude) — 공동 작성한 기록의 메모마다 무엇이 왜 고장 났고, 어떻게 고쳤고, 어떻게 확인했는지가 길게 적혀 있어요.
사람(저) — 윈도 컴퓨터에서 실제로 써 보고 증상을 알려 주고, 직접 시간을 재고, 무엇이 치명적인지 짚었어요. 메모에도 “사용자가 잰 값으로 결론이 났다” 같은 문장이 남아 있어요. PR 합치기 25건은 제 계정으로 기록돼 있어요.

7. 고장 하나에 검사 하나

첫날부터 습관이 하나 생겼어요. 고장을 고칠 때마다 검사를 하나씩 붙였어요. 고장 하나를 고치면, 같은 고장을 다시 잡아내는 검사 하나를 붙인다는 규칙이에요. 개발에서는 이런 검사를 회귀 테스트(regression test)라고 불러요.

고친 고장붙인 검사
윈도 드라이브 글자를 주소로 착각파일 위치를 그대로 넘기는 코드가 있으면 실패
두 컴퓨터가 부품 목록을 서로 고쳐 씀문제의 한 줄이 다시 생기면 실패
깔린 명령어 도구를 못 찾음정해 둔 실행 방법을 거치지 않으면 실패
설정 파일을 직접 고치라는 안내그런 안내가 문서·화면에 남아 있으면 실패
끈 뒤에도 남은 프로세스실제로 띄웠다 끄고 정말 사라졌는지 확인
압축판의 부품 누락그 컴퓨터용 부품이 들어 있는지 확인

이 검사들은 시험을 돌릴 때마다 먼저 실행되게 묶였고, 시험 항목(테스트)도 하루 사이에 0개 → 48개로 늘었어요. 첫날 생긴 검사 6개는 11주가 지난 지금도 하나도 지워지지 않고 남아 있어요. 검사를 지우지 않는 원칙은 31편에서 다시 이야기해요.

💡 핵심고장을 고친 날 검사도 함께 붙이면, 같은 고장이 다시 들어올 때 시험이 먼저 막아 줘요.

배운 점

AI와 하루를 짝으로 일해 보고 남은 것은 세 가지예요.
① 역할을 나눴어요. AI는 고치고 기록했고, 사람은 실제 컴퓨터에서 써 보고 판단했어요.
② 판단은 잰 값으로 했어요. 첫 답이 늦은 원인은 추측이 아니라 단계별로 잰 시간이 정했어요.
③ 고친 것은 검사로 남겼어요. 첫날의 검사 6개가 지금도 같은 고장을 막고 있어요.

✅ 한눈에 정리① 아침 첫 버전, 밤까지 판 16번
② 작업 기록 28개 모두 AI가 공동 작성
③ 사람은 써 보고, 재 보고, 판단
④ 고장 하나에 검사 하나 — 6개 그대로

자주 묻는 질문

Q. AI가 코드를 고치면 사람은 무엇을 했나요?

실제 윈도 컴퓨터에서 써 보고 증상을 알려 주고, 직접 시간을 재고, 무엇이 치명적인지 짚었어요. 저장 메모에도 '사용자가 잰 값으로 결론이 났다'는 문장이 남아 있어요.

Q. 공동 작성자 꼬리표는 무엇인가요?

저장 기록 끝에 붙는 'Co-Authored-By' 줄이에요. 이날 직접 작업한 기록 28개 모두에 Claude가 이 꼬리표로 올라 있어요.

Q. 맥에서 만든 프로그램이 윈도에서 왜 고장 났나요?

드라이브 글자, 명령어 도구가 깔리는 방식, 압축판에 들어간 부품이 맥과 달랐어요. 같은 고장이 다시 생기지 않게 고칠 때마다 검사를 붙였어요.
