yml 파일이란 — yaml 차이와 AI가 이 형식을 쓰는 이유 (캐릭터는 GPT 이미지 생성)

AI 도구를 조금만 깊이 쓰다 보면 .yml이라는 확장자가 자꾸 보여요. 자동 배포 설정도, AI에게 주는 규칙 파일도 이 형식이에요. “그래서 yml이 뭔데? 개발자만 쓰는 거 아냐?” 저도 처음엔 그렇게 넘겼는데, 지금 이 블로그를 굴리는 저장소에는 yml 파일이 390개 있어요.

장보기 메모를 떠올려 보세요. ‘과일’ 아래에 사과와 배를 한 칸 들여 쓰면, 누가 봐도 사과가 과일 항목이라는 걸 알죠. yml은 이 들여쓰기 메모를 프로그램도 알아듣게 규칙으로 정한 형식이에요.
YAML은 사람이 읽고 고치기 쉬우면서, 프로그램도 그대로 읽는 설정·데이터 형식이에요.

1. 뜻: 괄호를 뺀 데이터 메모

YAML은 괄호·따옴표 대신 들여쓰기로 구조를 만드는 데이터 형식이에요. 이름부터 농담이에요. “YAML Ain’t Markup Language”, 우리말로 ‘YAML은 마크업 언어가 아니다’를 줄인 말이에요.

공식 명세는 YAML을 ‘사람 친화적인 데이터 직렬화 언어’라고 소개해요. 직렬화는 데이터를 파일에 적을 수 있는 글자로 바꾸는 일이에요.

같은 내용을 JSON으로 쓰면 {"active": true, "tags": ["ai", "yml"]}처럼 괄호·따옴표·쉼표가 붙어요. YAML로 쓰면 이렇게 돼요.

active: true
tags:
  - ai
  - yml

괄호도 따옴표도 쉼표도 없어요. 들여쓰기가 곧 구조이고, 나머지는 거의 그냥 글자예요. 그래서 개발을 모르는 사람도 파일을 열어 읽고 고칠 수 있어요. 이게 이 형식의 전부이자 핵심이에요.

2. .yml과 .yaml은 같은 파일

.yml과 .yaml은 내용도 문법도 같아요. 확장자 이름만 달라요. 공식 권장 확장자는 .yaml이고, 2006년 YAML FAQ부터 그렇게 안내했어요(위키백과 YAML 문서 기준). .yml은 한 글자 줄인 표기예요.

GitHub 공식 문서도 자동 배포 설정(워크플로) 파일은 .yml이나 .yaml 둘 중 하나면 된다고 적어 두었어요.

PyYAML 같은 읽기 도구는 확장자가 아니라 파일 안의 글자를 읽어요. 다만 정해진 파일 이름을 찾는 도구도 있으니, 그때는 그 도구 설명서의 이름을 따르세요.
실무 기준은 하나예요. 프로젝트가 이미 쓰는 쪽을 따라가세요. 한 저장소 안에서 섞이면 “왜 이 파일만 다르지?” 하고 매번 멈칫하게 돼요. 저는 저장소 전체를 .yml로 통일했어요.

3. AI가 yml을 쓰는 세 가지 방법

AI 작업에서 yml은 규칙서, 작업 기록, 프로그램과 잇는 다리로 쓰여요. 사람이 읽는 문서이면서 동시에 프로그램이 읽는 데이터라서 가능한 일이에요.

yml 파일 하나를 사람·AI·스크립트가 함께 읽는 구조 (직접 제작)

① AI에게 주는 규칙서 — 이 블로그의 채널 규칙은 channels.yml에 적혀 있어요. 예를 들어 ‘네이버 리뷰 글에는 쿠팡 파트너스 링크 금지’가 한 줄로 들어 있어요. 매번 대화로 설명하는 대신 한 번 적어 두고, “channels.yml 규칙대로 바꿔줘”라고 말하면 돼요.

② AI가 남기는 작업 기록 — 글마다 상태 파일(content.yml)이 하나씩 있고, 지금 159개예요. 어디에 언제 발행했는지가 문장이 아니라 칸으로 남아요. “그 글 네이버에도 올렸던가?”를 기억에 기대지 않아도 돼요.

③ AI와 프로그램을 잇는 다리 — 대시보드를 만드는 파이썬 스크립트가 이 상태 파일을 전부 모아 읽어요. AI가 yml을 쓰고, 파이썬이 읽고, 사람은 브라우저로 봐요.

규칙 바인더를 펴 놓고 작업 일지를 쓰는 로봇 — yml을 규칙서이자 기록으로 쓰는 장면 (GPT 이미지 생성)

이미 매일 보고 계실 수도 있어요. GitHub 자동 배포 설정이 이 형식이고, 클로드 코드 서브에이전트 정의 파일의 맨 위 칸(프론트매터)도 YAML이에요. 대화창에 적은 규칙은 그 대화가 끝나면 사라지지만, 파일은 남아요.

💡 핵심AI에게 두 번 넘게 한 설명은 yml 파일로 적어 두세요.

4. yml이 실제로 잡아낸 실수

9월 8일, AI가 yml 파일 두 종류를 대조해서 설정과 현실이 어긋난 걸 찾아냈어요. “지금 채널 몇 개 돌리고 있지?”라고 물었더니, AI가 설정 파일(channels.yml)과 글마다 붙은 발행 기록(content.yml)을 맞대 보고 이렇게 답했어요.

“네이버 리뷰 채널이 설정에는 꺼짐(active: false)인데, 실제로는 7건이 발행됐어요.”

채널을 만들고 글은 계속 올렸는데, 설정 파일만 안 고쳤던 거예요. 두 파일이 다른 폴더에 있고 기록 쪽은 그때도 32개로 흩어져 있어서, 눈으로는 못 잡는 실수였어요. 교훈은 둘이에요. yml로 적어 두면 AI가 점검을 대신 해 줘요. 그리고 yml은 스스로 바뀌지 않아요. 현실이 바뀌면 파일도 고치고, 가끔 대조를 시켜야 해요.

📋 그대로 복사해 쓰세요

설정 파일과 실제 기록 파일을 대조해서, 서로 안 맞는 항목을 찾아줘

5. 문법 함정 4가지

함정은 네 가지예요. 참·거짓으로 바뀌는 글자, 0이 사라지는 숫자, 값 안의 콜론, 탭 들여쓰기. 이 저장소의 PyYAML 6.0.3으로 오늘 다시 돌려 본 결과예요.

내가 쓴 것실제로 읽히는 값
active: yesTrue — yes·no·on·off는 참·거짓
country: NOFalse — 국가 코드 NO도 거짓
version: 1.201.2 — 숫자로 읽혀 끝의 0이 사라짐
title: 제목: 부제에러 — 값 속 콜론을 구조로 읽음
탭으로 들여쓰기에러 — 들여쓰기는 스페이스만

해결은 대부분 같아요. 헷갈리면 따옴표로 감싸세요. active: “yes”, version: “1.20”, title: “제목: 부제”처럼 감싸면 쓴 글자 그대로 읽혀요.

참·거짓과 숫자 함정은 에러도 없이 조용히 다른 값이 돼서 더 위험해요.

탭은 공식 명세가 못 박은 규칙이에요. ‘이식성을 위해 들여쓰기에 탭 문자를 쓰면 안 된다. 시스템마다 탭을 다르게 다루기 때문이다.’ 에디터에서 Tab 키가 스페이스로 들어가게 설정해 두는 게 가장 확실한 예방책이에요.

6. 오늘 만드는 첫 yml

AI에게 매번 반복해서 설명하는 것을 파일로 빼면, 그게 첫 yml이에요.

  1. 메모장을 열고 아래 네 줄을 그대로 적으세요.
톤: 존댓말, 과장 금지
구조: 결론을 맨 앞에
금지: 확인 안 된 수치를 확정해서 쓰기
제목형식: "핵심 먼저: 설명은 뒤에"
  1. my-rules.yml이라는 이름으로 저장하세요.
  2. AI와 대화를 시작할 때 파일을 건네고 아래 한 줄을 붙이세요.→ 클로드 코드처럼 파일을 읽는 도구라면 같은 폴더에 두기만 해도 돼요. 채팅 AI라면 파일을 첨부하세요.
my-rules.yml 규칙을 지켜서 써줘

맨 아랫줄만 따옴표가 있죠? 값 안에 콜론이 들어 있어서예요. 만들 때 지킬 것은 세 가지예요. 한 파일에는 한 주제만, 항목 이름은 짧고 일관되게(값은 한글도 괜찮아요), 날짜와 이유는 주석으로. 줄 맨 앞에 샵 기호와 띄어쓰기를 두면, 프로그램이 읽지 않는 메모가 돼요. 3주 뒤의 나는 왜 이렇게 정했는지 기억하지 못해요.

⚠️ 주의비밀번호·API 키는 yml에 적지 마세요. 규칙 파일은 AI도 사람도 다 읽어요. 이 블로그는 키를 별도 파일(.env)에 따로 둬요.

헷갈리기 쉬운 것

yml은 프로그래밍 언어가 아니에요 계산하거나 실행하는 기능이 없어요. 데이터를 적어 두는 형식이고, 실행은 그걸 읽는 프로그램이 해요.

yml과 마크다운(md)은 다른 형식이에요 마크다운은 사람이 읽는 글을 꾸미는 형식이고, yml은 프로그램이 읽을 항목을 적는 형식이에요. 다만 마크다운 글 맨 위 ‘---’ 사이 칸(프론트매터)은 YAML로 써요. 이 글 사이트판의 제목과 키워드도 거기 적혀 있어요.

JSON으로 써도 되지만, 손으로 고치기는 yml이 편해요 JSON은 프로그램끼리 주고받기 좋고, 사람이 직접 손보기엔 괄호와 쉼표가 번거로워요. 사람이 자주 고치는 규칙 파일이라면 yml이 편해요.

자주 묻는 질문

Q. yml 파일은 무엇으로 여나요?

메모장 같은 글 편집기로 열고 고칠 수 있어요. 특별한 프로그램은 필요 없어요.

Q. 들여쓰기는 몇 칸이어야 하나요?

같은 단계끼리 칸 수만 맞으면 돼요. 이 블로그의 yml은 두 칸씩 써요. 탭은 쓰면 안 돼요.

Q. 코딩을 몰라도 yml을 쓸 수 있나요?

네. 6번처럼 ‘이름: 값’ 줄만 적어도 첫 yml이 돼요. 목록처럼 들여쓰는 구조는 AI에게 만들어 달라고 하고, 사람은 읽고 고치면 돼요.

Q. .yml과 .yaml 중 무엇을 써야 하나요?

공식 권장은 .yaml이지만 둘은 같은 형식이에요. 프로젝트가 이미 쓰는 쪽에 맞추세요.

6절의 네 줄을 목록으로 늘린 모양이에요. 콜론이 든 값만 따옴표로 감쌌어요.

# my-rules.yml — AI에게 매번 설명하던 것들 (작성 날짜를 적어 두세요)

톤:
  - 존댓말, 과장 금지
  - 결론을 맨 앞에

금지:
  - 확인 안 된 수치를 확정해서 쓰기
  - 회사 이름·고객 정보 언급

형식:
  분량: "A4 1장 이내"
  제목형식: "핵심 먼저: 설명은 뒤에"

부록: 이 블로그의 실제 파일 일부

규칙서 — config/channels.yml의 네이버 리뷰 채널 규칙(일부):

naver_review:
  active: true
  rules:
    - 쿠팡 파트너스 링크 금지 (저품질 위험 — 자체 사이트 전용)
    - 협찬 글은 공정위 표기 필수
