LLM 위키 뜻, 카파시가 제안한 AI 지식 정리법과 RAG 차이

LLM 위키 뜻과 구조 — AI가 키우는 나만의 백과사전 (캐릭터는 GPT 이미지 생성)

AI에게 자료를 잔뜩 주고 질문하면 매번 같은 일이 벌어져요. 자료를 처음부터 다시 뒤지고, 지난주에 낸 결론을 이번 주에 또 내요. “그 사이 배운 건 다 어디 갔지?”

냉장고에 메모지가 아무리 많이 붙어 있어도 살림이 정리되지 않는 것과 같아요. 메모지끼리 서로를 모르니까요. LLM 위키는 이 문제를 ‘AI에게 메모지 대신 백과사전을 맡기자’로 풀어요.
LLM 위키는 AI가 읽은 자료를 정리하고 서로 연결해, 스스로 키워 가는 마크다운 백과사전이에요.

흩어진 메모지를 책으로 묶어 서가에 꽂는 로봇 사서 — LLM 위키를 빗댄 그림 (GPT 이미지 생성)

🎯 이 글에서 얻는 것대상: LLM 위키라는 말이 낯선 분
① LLM 위키 뜻과 사서 비유
② 3층 구조와 AI가 하는 일 세 가지
③ RAG와의 차이, 오늘 시작하는 법
2026년 10월 기준 · 카파시 원문(2026년 4월)

1. 뜻: 카파시가 제안한 방식

LLM 위키는 2026년 4월 4일 안드레 카파시가 GitHub에 올린 문서 한 장에서 나온 이름이에요. 카파시는 테슬라에서 AI 총괄(Director of AI)을 지냈고, OpenAI 창립 멤버예요.

그가 제안한 건 원본 자료와 나 사이에 ‘구조화되고 서로 연결된 마크다운 파일 묶음’을 두고, AI가 그걸 ‘조금씩 만들고 유지’하게 하는 방식이에요. 핵심 단어는 ‘누적되는 산출물(compounding artifact)’이에요. 질문마다 새로 만드는 답이 아니라, 쓸수록 쌓여 가는 물건이라는 뜻이에요.

원문은 스스로를 ‘일부러 추상적으로 쓴 글’, ‘구현이 아니라 아이디어’라고 밝혀요. 그래서 폴더 구조나 페이지 형식은 자기 주제에 맞게 정하면 돼요. 원문은 클로드 코드나 OpenAI Codex 같은 AI 에이전트에 그대로 붙여 넣어 쓰는 아이디어 파일이라고도 적어 두었어요.

2. 구조: 3층과 AI가 하는 일

실체는 폴더 세 칸이에요. 원본은 그대로 두고, 위키는 AI가 쓰고, 규칙은 사람이 써요.

LLM 위키의 3층(규칙·위키·원본)과 AI가 하는 일 세 가지 (직접 제작)

원본은 논문·기사·회의록처럼 내가 모은 자료예요. 서가의 책처럼 AI는 읽기만 하고 고치지 않아요.
위키는 AI가 쓰는 정리 페이지예요. 요약, 개념 페이지, 비교, 기록까지 AI가 전부 맡아요. 사서의 노트예요.
규칙은 어떻게 정리할지 적은 안내문이에요. 카파시는 CLAUDE.md나 AGENTS.md 같은 설정 문서를 예로 들었어요. 사서에게 건넨 업무 지침이에요.

이 위에서 AI가 하는 일은 세 가지예요.

동작하는 일
넣기 (ingest)새 자료를 읽고 요약을 쓰고, 관련 페이지를 고치고, 기록을 남김
묻기 (query)위키부터 찾아 근거를 달아 답하고, 좋은 답은 새 페이지로 저장
점검 (lint)모순·낡은 주장·외톨이 페이지·빠진 연결을 찾아 고침

셋째가 재미있는 부분이에요. 위키도 사람의 노트처럼 틀리고 낡아요. 그래서 대청소 날이 따로 있어요.

3. RAG와 뭐가 다른가

차이는 한 단어, 누적이에요. RAG는 질문마다 원본을 다시 찾고, LLM 위키는 정리해 둔 위키 위에 쌓아요. RAG(검색 증강 생성)는 질문이 오면 원본에서 관련 부분을 찾아 AI에게 건네는 방식이에요. 카파시는 이걸 ‘질문마다 지식을 처음부터 다시 찾는 방식’이라고 짚었어요.

사서 둘을 떠올리면 쉬워요. 첫 번째 사서는 질문을 받을 때마다 서가로 뛰어가 책을 뒤지고, 답한 뒤 책을 제자리에 꽂아요. 어제 같은 질문을 받았어도 기억하지 않아요. 두 번째 사서는 새 책이 들어오면 읽고, 자기 노트에 요약을 적고, 이미 있는 노트와 연결선을 그어요. 질문이 오면 서가가 아니라 자기 노트부터 봐요.

질문마다 서가로 뛰어가는 사서와 자기 노트부터 펴는 사서 — RAG와 LLM 위키를 빗댄 그림 (GPT 이미지 생성)

두 방식을 나란히 놓으면 이래요.

구분RAG → LLM 위키
질문이 오면원본을 처음부터 검색 → 정리된 위키부터 봄
시간이 지나면남는 것 없음 → 위키가 두꺼워짐
AI의 역할검색기·요약기 → 편집자·사서
잘 맞는 곳자료가 아주 많을 때 → 한 주제를 오래 팔 때

둘 중 하나가 옳은 건 아니에요. 자료가 수만 건이거나 여러 사람이 동시에 쓰면 RAG가 맞고, 개인이나 작은 팀이 한 주제를 오래 파면 위키가 맞아요.

💡 핵심질문할 때마다 찾게 하지 말고, 읽을 때마다 정리하게 하세요.

4. 실물: 제 블로그는 이미 위키였어요

카파시 글을 읽고 제 저장소를 세어 보니, 3층 구조가 이미 그대로 있었어요. 9월 9일 기준으로 AI와 제가 같이 쓰는 마크다운이 5,869줄이었어요. 그중 날짜가 박힌 학습 메모가 17개, 글마다 붙은 상태 파일이 39개, 운영 문서가 12개, AI가 저에 대해 기억해 둔 메모가 6개였어요.

원본(리뷰·사진 자료)은 건드리지 않고, 정리 문서는 AI가 쓰고, 규칙 파일은 제가 승인해요. 누가 시킨 적 없는데 그렇게 돼 있었어요.

이게 실제로 뭘 해 주는지는 9월 8일 하루가 보여 줬어요.
아침 8시 50분 네이버 발행 자동화가 숨은 버튼을 잘못 잡아 30초 시간 초과가 났고, AI가 원인과 올바른 선택 방법을 문서에 적었어요.
그날 저녁까지 네이버 발행 7건, 같은 시간 초과는 0번이었어요. 매번 그 문서를 먼저 읽고 시작했으니까요.
밤 9시 51분 다른 블로그의 카테고리 이름에 보이지 않는 공백이 섞여 선택이 실패했고, 그것도 문서에 추가됐어요.

RAG였다면 매번 대화 기록을 뒤져 ‘지난번에 뭐가 문제였지’를 다시 찾았을 거예요. 대화가 끝나면 그 기억도 사라졌을 거고요.

5. 위키라서 생기는 함정

위키는 쌓이는 만큼 낡고 틀릴 수도 있어요. 그래서 지킬 것이 네 가지 있어요.
원본은 AI가 고치게 두지 마세요. 위키가 틀렸을 때 돌아갈 곳이 원본이에요. 카파시가 원본 층을 ‘바뀌지 않는 층’으로 둔 이유예요.
점검 주기를 정하세요. 넣기만 하고 점검을 안 하면 6개월 전 결론이 오늘의 답이 돼요. 저는 수익 가정을 90일마다 실제 숫자와 비교하도록 정해 두었어요.
처음부터 큰 구조를 짜지 마세요. 폴더 하나, 규칙 한 장, 자료 다섯 개면 충분해요. 위키는 쓰면서 모양이 잡혀요.
위키의 답도 확인하세요. 근거 페이지가 달려 있어 확인이 쉬워질 뿐, 안 해도 되는 건 아니에요.

⚠️ 주의회사 문서나 개인 정보는 원본 폴더에 넣기 전에, 그 AI 도구에 넣어도 되는 자료인지 먼저 확인하세요.

6. 오늘 저녁에 시작하는 법

설치할 프로그램이 아니라 방식이라, 폴더 하나와 규칙 파일 한 장이면 시작할 수 있어요.

  1. 폴더를 하나 만들고, 그 안의 원본 폴더에 자료 다섯 개를 넣으세요.→ PDF, 메모, 저장한 웹 페이지 무엇이든 괜찮아요.
  2. 규칙.md 파일을 만들고 아래 네 줄을 적으세요.
자료마다 요약 페이지 하나
등장하는 개념마다 개념 페이지 하나
페이지끼리 서로 링크로 연결
원본 폴더의 파일은 수정 금지
  1. 파일을 다루는 AI 도구(클로드 코드 등)를 그 폴더에서 켜고 아래처럼 시키세요.→ 위키 폴더에 요약 페이지와 개념 페이지가 만들어져요.

📋 그대로 복사해 쓰세요

규칙.md대로 원본 폴더를 읽고 위키 폴더에 정리해줘
  1. 새 자료가 생기면 원본 폴더에 넣고 “이것도 위키에 반영해줘”라고 하세요.→ 여기서부터 위키가 쌓이기 시작해요.
  2. 일주일에 한 번은 점검을 시키세요.
위키에서 서로 모순되는 페이지와 오래된 주장을 찾아줘

카파시는 위키를 들여다보는 창으로 옵시디언(Obsidian)을 썼어요. 원문 비유는 “Obsidian은 IDE, LLM은 프로그래머, 위키는 코드베이스”예요. 옵시디언으로 보고, AI가 쓰고, 위키가 결과물로 쌓인다는 뜻이에요.

헷갈리기 쉬운 것

LLM 위키는 프로그램 이름이 아니에요 내려받아 설치하는 도구가 아니라, 폴더와 규칙으로 AI에게 정리를 맡기는 방식이에요. 원문도 특정 구현이 아니라 아이디어라고 밝혀요.

위키백과와는 상관없어요 여러 사람이 함께 쓰는 공개 백과사전이 아니라, 나와 AI가 쓰는 개인 문서 묶음이에요. 이름의 ‘위키’는 페이지끼리 링크로 이어진 문서 모음이라는 뜻이에요.

위키가 커지면 검색이 필요해요 원문도 작을 때는 목차 파일 하나로 충분하지만, 위키가 커지면 제대로 된 검색이 필요하다고 적어요. 누적과 검색은 함께 쓸 수 있어요.

자주 묻는 질문

Q. LLM 위키를 만들려면 코딩을 알아야 하나요?

아니요. 폴더와 규칙 파일 한 장, 그리고 파일을 다루는 AI 도구가 있으면 6번 순서대로 시작할 수 있어요.

Q. 어떤 AI 도구로 만들 수 있나요?

폴더의 파일을 읽고 쓰는 AI 에이전트면 돼요. 카파시 원문은 OpenAI Codex와 클로드 코드를 예로 들었고, 보는 창으로는 옵시디언을 썼어요.

Q. RAG보다 항상 나은가요?

아니요. 자료가 수만 건이거나 여러 사람이 동시에 쓰면 RAG가 맞아요. 한 주제를 오래 파는 개인과 작은 팀에 위키가 잘 맞아요.

Q. 위키 내용이 틀리면 어떻게 하나요?

원본으로 돌아가 확인하고, 점검을 시켜 고치게 하세요. 그래서 원본은 고치지 않고 그대로 둬요.
