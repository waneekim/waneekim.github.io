클로드 코드 사용법, 설치 다음에 꼭 알아야 할 6가지

클로드 코드 사용법 — 설치 다음에 꼭 알아야 할 6가지 (캐릭터는 GPT 이미지 생성)

클로드 코드를 설치하고 나면 이 질문에서 멈추게 돼요. “그래서 뭘 어떻게 시키지?” 명령어 목록부터 외워야 하나 싶지만, 그럴 필요는 없어요.

클로드 코드는 말귀 밝은 신입 동료와 비슷해요. 할 일을 말하면 계획을 세우고, 위험한 일은 결재를 받게 할 수 있고, 시키면 확인까지 해요.
사용법의 핵심은 명령어가 아니라 일을 맡기는 순서예요.

새 동료에게 업무 매뉴얼을 건네는 장면 (GPT 이미지 생성)

준비물: 설치한 클로드 코드 · 작업할 폴더
2026년 10월 기준 · Windows 11 · 2.1.268

1. 폴더에서 켜고, 말로 시키기

클로드 코드는 작업할 폴더 안에서 켜고, 할 일을 한국어로 말하면 돼요. 파일을 찾고 고치고 명령을 실행하는 일은 클로드 코드가 알아서 해요.

  1. 터미널을 열고 cd 명령으로 작업할 프로젝트 폴더에 들어가세요.→ 입력 줄 맨 앞에 그 폴더 경로가 보여요.
  2. 아래 두 줄을 한 줄씩 입력하세요.
claude --version
claude

→ 첫 줄은 설치된 버전을 보여 줘요. 이 머신에서는 2.1.268이 떠요.
→ 둘째 줄로 클로드 코드가 켜지면, 그다음부터는 채팅하듯 한국어로 시키면 돼요.

제가 이 블로그 저장소에서 실제로 입력했던 요청이에요.

📋 그대로 복사해 쓰세요

이 저장소 구조를 파악하고 실행 계획 문서를 만들어줘

파일을 어떻게 고칠지가 아니라, 무엇이 되어 있어야 하는지를 말하세요. “방금 만든 글을 사이트에 배포해줘”처럼 결과만 말해도 실제로 일이 돌아갔어요.

클로드 코드에 일을 맡기는 순서 — 목표 말하기, 계획 확인, 실행, 결과 확인, 다듬기 (직접 제작)

2. CLAUDE.md로 규칙 남기기

프로젝트 폴더 맨 위에 CLAUDE.md 파일을 두면, 클로드 코드가 세션을 시작할 때마다 읽어요. 신입 동료에게 건네는 업무 매뉴얼이라고 보면 돼요. 같은 설명을 매번 되풀이하지 않아도 돼요.

CLAUDE.md 규칙 예시

커밋 메시지에 큰따옴표를 넣지 말 것 (PowerShell 인자 분리 문제)
비밀 값(.env)은 어떤 로그에도 출력하지 말 것
문서는 한국어로 작성

써 보니 이 파일은 같은 실수를 되풀이하지 않게 만드는 데 가장 쓸모 있었어요.

💡 핵심같은 지적을 두 번 했다면, 그 내용은 CLAUDE.md에 적어 두세요.

3. 큰 작업은 계획 모드로

구조를 바꾸는 큰 작업은 계획 모드(plan mode)에서 계획부터 받으세요. 작은 수정은 바로 시켜도 되지만, 계획 모드에서는 파일을 고치지 않고 계획만 세워 승인을 받아요.

  1. 입력 칸에서 Shift+Tab을 누르세요.→ 누를 때마다 권한 모드가 바뀌어요. 상태 줄에 plan mode on이 보이면 계획 모드예요.
  2. 할 일을 평소처럼 말하세요.→ 파일은 그대로 두고, 무엇을 어떻게 바꿀지 계획을 보여 줘요.
  3. 계획을 읽고 방향이 맞으면 승인하세요.→ 그때부터 실제로 파일을 고쳐요.

이 블로그 시스템의 뼈대도 이렇게 만들었어요. 계획 문서를 먼저 받아 검토하고, 방향이 맞을 때 실행시켰어요. 되돌리기 어려운 작업일수록 계획 모드라고 기억하세요.

4. 권한 승인 기준 정하기

수동(Manual) 모드에서 클로드 코드는 파일을 고치거나 명령을 실행하기 전에 승인을 요청해요. 처음엔 귀찮게 느껴지지만, 쓰다 보면 이 승인 단계가 안심하고 맡길 수 있는 이유예요.

다만 버전과 요금제에 따라 처음부터 자동(auto) 모드로 켜지기도 해요. 자동 모드에서는 사람 대신 검사용 모델이 작업을 살피고, 위험해 보이는 것만 막아요. 하나하나 직접 승인하고 싶다면 Shift+Tab으로 모드를 바꾸세요.

신입 동료가 위험한 일 앞에서 결재를 받으러 오는 장면 (GPT 이미지 생성)

제 운영 원칙은 세 줄이에요.
읽기·검색 — 자유롭게 맡겨요.
쓰기·실행 — 자동 모드로 맡겨요. 위험해 보이는 건 검사 모델이 막아요.
외부 발행(배포·게시) — 규칙을 정해 두고 맡겨요.

발행도 처음엔 매번 직접 승인했어요. 손에 익은 뒤에 ‘하루 1편씩 발행 큐로’, ‘발행 전 자동 검사’ 같은 규칙을 정하고 맡겼어요. 새 채널에 처음 올리는 글은 지금도 화면을 보고 직접 승인하고, 커밋은 제가 시킬 때만 해요.

수동 모드로 쓰면서 매번 승인하기 번거로우면, 승인 창에서 ‘다시 묻지 않기(don’t ask again)‘를 고를 수 있어요. 파일 수정은 그 세션이 끝날 때까지, 셸 명령은 그 저장소에서 계속 다시 묻지 않아요.

사고가 없지는 않았어요. 한 번은 자동화가 엉뚱한 편집 창의 글을 발행해서 바로 되돌렸어요. 그 뒤로 발행 전에 편집 창이 하나뿐인지부터 확인하게 했어요.

⚠️ 주의배포·게시 명령에는 '다시 묻지 않기'를 고르지 마세요. 셸 명령 허용은 세션이 끝나도 그 저장소에 남아요.

5. 매일 쓰는 명령 6개

매일 쓰는 건 아래 여섯 개예요. 다 외울 필요는 없어요.

입력하는 일
/help명령 목록 보기 — 모르면 이것부터
/clear대화 비우기 — 새 작업을 시작할 때
/compact대화 요약 압축 — 긴 작업에서 맥락 유지
Esc진행 중인 작업 멈추기
@파일명특정 파일을 대화에 불러오기
!명령어셸 명령 바로 실행 (예: !git status)

단축키와 명령은 버전에 따라 바뀔 수 있어요. /help가 늘 지금 버전의 정답이에요. 위 여섯 개는 공식 문서(2026년 10월 6일 확인)와 대조했어요.

6. 잘 시키는 요령 3가지

첫째, 검증 기준을 같이 주세요. 클로드 코드는 실행하고 확인까지 할 수 있어서, 검증을 요청에 넣으면 스스로 오류를 잡아요.

❌ 이렇게 말고

스크립트 만들어줘

무엇이 되면 끝인지가 빠져 있어요.

⭕ 이렇게

스크립트를 만들고 실행해서, 결과 URL이 열리는 것까지 확인해줘

제가 써 보니 검증을 요청에 넣는 것만으로도 결과가 훨씬 좋아졌어요.

둘째, 실수는 규칙으로 만드세요. 잘못한 걸 발견하면 그 자리에서 고치게 하고, 같은 실수가 다시 나오지 않도록 CLAUDE.md에 적게 하세요.

셋째, 긴 작업은 중간 보고를 시키세요. 요청 끝에 이 한 줄을 붙이면, 방향이 어긋나기 전에 잡을 수 있어요.

각 단계가 끝날 때마다 결과를 알려줘

막힐 때

작업이 엉뚱한 방향으로 가요
원인: 대개 중간에 확인할 지점 없이 긴 작업을 한 번에 맡겼을 때예요.
해결: Esc로 멈추세요. 그때까지 한 작업은 남아 있어요. 방향을 다시 말하고, 큰 작업이면 계획 모드로 계획부터 받으세요.

대화가 길어지니 앞에서 정한 내용을 놓쳐요
원인: 대화가 쌓여 맥락 창이 차면 앞에서 한 지시를 놓치기 쉬워요.
해결: /compact로 대화를 요약해 줄이세요. 아예 다른 작업이면 /clear로 새로 시작하세요.

승인 요청이 너무 자주 떠요
원인: 수동 모드는 파일 수정과 명령 실행마다 승인을 물어요.
해결: 자주 하는 작업은 승인 창에서 ‘다시 묻지 않기’를 고르세요. 배포·게시 명령은 빼고요.

✅ 한눈에 정리① 폴더에서 켜고, 결과를 말로 시켜요
② 반복되는 지적은 CLAUDE.md에 적어요
③ 큰 작업은 계획 모드로 계획부터 받아요
④ 밖으로 나가는 일은 처음엔 직접 승인해요

자주 묻는 질문

Q. 명령어를 다 외워야 하나요?

아니요. 매일 쓰는 건 5번의 여섯 개 정도이고, 모르는 건 /help가 지금 버전 기준으로 알려 줘요.

Q. 한국어로 시켜도 되나요?

네. 1번의 두 요청은 제가 실제로 한국어로 입력한 그대로예요. CLAUDE.md에 '문서는 한국어로 작성'처럼 적어 두면, 매번 말하지 않아도 세션마다 그 규칙을 읽고 시작해요.

Q. 코드를 몰라도 시킬 수 있나요?

무엇이 되어 있어야 하는지를 말하면, 파일 탐색과 코드 수정과 명령 실행은 클로드 코드가 해요. 결과를 확인하고, 밖으로 내보내는 규칙을 정하는 건 사람이 해요.

Q. 계획 모드는 언제 쓰나요?

구조를 바꾸거나 되돌리기 어려운 작업일 때요. 작은 수정은 바로 시켜도 돼요.

다음 글에서는 CLAUDE.md 같은 ‘부탁’ 대신, 정해진 시점에 무조건 실행되는 규칙인 훅(hooks)을 다뤄요.
